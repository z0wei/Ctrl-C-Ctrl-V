## 📌 1. Что такое контроль доступа

Контроль доступа — это ограничения на то, кто и что может делать в приложении.

Он зависит от двух других механизмов:

| Компонент | Что делает |
| :--- | :--- |
| Аутентификация | Подтверждает, что пользователь — это тот, за кого себя выдаёт. |
| Управление сессиями | Определяет, что последующие запросы отправляются тем же пользователем. |
| Контроль доступа | Решает, разрешено ли пользователю выполнять запрошенное действие. |

> Запомни: Аутентификация ≠ Авторизация. Первая — это кто ты, вторая — что тебе можно.

---

## 🔍 2. Типы контроля доступа

### Вертикальный контроль доступа (Vertical Access Control)

Разные пользователи имеют доступ к разным функциям.

| Кто | Что может |
| :--- | :--- |
| Администратор | Удалять пользователей, менять настройки |
| Обычный пользователь | Только свои данные |

Нарушение: Обычный пользователь получает доступ к /admin.

---

### Горизонтальный контроль доступа (Horizontal Access Control)

Разные пользователи имеют доступ к одним и тем же функциям, но к разным данным.

Пример: Пользователь alice видит только свои заказы, bob — только свои.

Нарушение: alice меняет order_id=123 на 124 и видит заказ bob — это IDOR.

---

### Контекстно-зависимый контроль доступа (Context-Dependent Access Control)

Доступ зависит от состояния приложения или порядка действий.

Пример: Нельзя изменить корзину после оплаты.

Нарушение: Можно пропустить шаги и сразу подтвердить заказ.

---

## 🛠️ 3. Основные уязвимости контроля доступа

### 3.1. Незащищённая функциональность (Unprotected Functionality)

Админ-панель доступна по прямому URL, но ссылка на неё скрыта.

Где искать:
- robots.txt
- JavaScript-код
- Комментарии в HTML
- Перебор директорий (/admin, /administrator, /panel)

---

### 3.2. Безопасность через сокрытие (Security by Obscurity)

Админ-панель находится по сложному URL, но он раскрыт в коде.

Пример:
```javascript
if (isAdmin) {
    window.location.href = '/administrator-panel-yb556';
}
```
Ты видишь URL в коде и переходишь по нему.

---

### 3.3. Контроль доступа через параметры

Роль пользователя хранится в клиент-контролируемом месте.

| Где хранится | Пример | Как взломать |
| :--- | :--- | :--- |
| Кука | roleid=1 | Изменить на roleid=2 |
| Скрытое поле | `<input type="hidden" name="role" value="user">` | Изменить на admin |
| Параметр URL | ?admin=false | Изменить на true |

Примеры:
```
https://site.com/login/home.jsp?admin=true
https://site.com/login/home.jsp?role=1
```

---

### 3.4. Обход через платформенные заголовки

Некоторые фреймворки позволяют переопределять URL или метод через заголовки.

#### X-Original-URL — подмена пути
```
POST / HTTP/1.1
X-Original-URL: /admin/deleteUser
...
```
Сервер обрабатывает /admin/deleteUser, а не /.

#### X-HTTP-Method-Override — подмена метода
```
POST /admin/deleteUser HTTP/1.1
X-HTTP-Method-Override: GET
```
Сервер обрабатывает как GET.

Другие заголовки:

| Тип заголовка | Заголовки | Когда использовать |
| :--- | :--- | :--- |
| **Подмена пути** | `X-Original-URL`, `X-Rewrite-URL`, `X-Original-URI` | Когда фильтр проверяет один URL, а бэкенд обрабатывает другой. |
| **Подмена метода** | `X-HTTP-Method-Override`, `X-HTTP-Method`, `X-Method-Override` | Когда защита настроена только на определённый метод. |
| **Подмена IP** | `X-Forwarded-For`, `X-Real-IP` | Когда доступ ограничен по IP-адресу. |
| **Подмена хоста** | `X-Forwarded-Host` | Когда доступ ограничен по домену. |
| **Подмена протокола** | `X-Forwarded-Proto`, `Front-End-Https` | Когда проверяется использование HTTPS. |

---

### 3.5. Обход через подмену метода HTTP

Если защита настроена только на POST, можно использовать другие методы.

Пример:
- Запрещён POST /admin/delete
- Разрешён GET /admin/delete?username=carlos

Как проверить: просто замени метод в запросе.

Методы для тестирования:
- GET
- POST
- PUT
- PATCH
- DELETE
- OPTIONS
- HEAD
- TRACE

---

### 3.6. Обход через несоответствия в URL

Системы могут по-разному обрабатывать URL.

| Техника | Пример |
| :--- | :--- |
| Регистр | /ADMIN/DELETEUSER вместо /admin/deleteUser |
| Суффикс | /admin/deleteUser.anything (Spring useSuffixPatternMatch) |
| Слеш в конце | /admin/deleteUser/ |

---

### 3.7. IDOR (Insecure Direct Object Reference)

Подкатегория уязвимостей контроля доступа.

Пример:
```
https://site.com/myaccount?id=123
```
Меняешь id=123 на 124 и видишь профиль другого пользователя.

Типы ID:
- id=123 — числовой (легко перебрать)
- user=carlos — строковый (можно угадать)
- hash=abc123def456 — хеш (трудно, но можно)
- guid=123e4567-e89b-12d3-a456-426614174000 — GUID (почти невозможно)

Где найти GUID другого пользователя:
- Комментарии и отзывы
- Ссылки на профили
- Заказы и транзакции
- Внутренние API
- Ссылки на скачивание файлов

---

### 3.8. Утечка данных через редирект

Приложение возвращает редирект на страницу входа, но тело ответа уже содержит данные.

Пример:
```http
HTTP/2 302 Found
Location: /login
Content-Type: text/html
Content-Length: 2048

<ul>
    <li>alice: alice@example.com</li>
    <li>carlos: carlos@example.com</li>
</ul>
```

Что делать: Перехватывай ответы в Burp, даже если там 302.

---

### 3.9. Многоэтапные процессы

Проверка прав есть на первых шагах, но отсутствует на последнем.

Пример:
1. Загрузка формы (проверка ✅)
2. Отправка изменений (проверка ✅)
3. Подтверждение (❌ НЕТ ПРОВЕРКИ!)

Атака: Пропустить шаги 1-2 и отправить запрос на шаг 3 напрямую.

---

### 3.10. Контроль доступа по Referer

Доступ к подстраницам проверяется по заголовку Referer.

Проблема: Referer можно подделать.

Атака:
```
GET /admin/deleteUser?username=carlos
Referer: https://site.com/admin
```

---

### 3.11. Контроль доступа по геолокации

Доступ ограничен по IP/стране.

Обход: VPN, прокси, подделка X-Forwarded-For.

## 🔄 4. Повышение привилегий (Privilege Escalation)

### Вертикальное повышение (Vertical Privilege Escalation)
Получение доступа к функциям выше своей роли (становишься админом).

### Горизонтальное повышение (Horizontal Privilege Escalation)
Получение доступа к данным другого пользователя.

### От горизонтального к вертикальному
Компрометация администратора через горизонтальную атаку.

Пример:
1. Находишь ID администратора через IDOR.
2. Заходишь на его страницу.
3. Сбрасываешь его пароль.
4. Заходишь как администратор.

## 🛡️ 5. Как защититься

Принципы предотвращения уязвимостей:

| Принцип | Описание |
| :--- | :--- |
| Не полагайся на сокрытие | Скрытый URL — не защита. |
| Запрещай по умолчанию | Если ресурс не публичный — доступ запрещён. |
| Единый механизм | Используй одну систему контроля доступа во всём приложении. |
| Явные разрешения | Разработчики должны указывать, кому разрешён доступ. |
| Тестирование | Проверяй контроль доступа в каждом запросе. |

## 🧰 6. Чек-лист для пентеста

1. Найди все административные пути (robots.txt, JS, фаззинг).
2. Проверь доступ к /admin и другим подозрительным путям.
3. Проверь куки, параметры, скрытые поля на наличие role, admin, isAdmin.
4. Попробуй изменить ID (user_id=1 → 2).
5. Попробуй подменить метод (POST → GET, PUT, PATCH, DELETE).
6. Попробуй добавить заголовки X-Original-URL, X-HTTP-Method-Override.
7. Проверь Referer — подставь Referer: https://site.com/admin.
8. Проверь регистр, суффиксы, слеши в URL.
9. Проверь многошаговые процессы — пропусти шаги.
10. Проверь редиректы — перехватывай ответы с 302.
11. Используй Burp Intruder для перебора ID и директорий.
12. Проверь ответы на наличие утечек данных даже при 403/401.

## 🧠 7. Ключевые термины

| Термин | Объяснение |
| :--- | :--- |
| IDOR | Подмена ID для доступа к чужим данным. |
| Вертикальное повышение | Доступ к функциям выше своей роли. |
| Горизонтальное повышение | Доступ к данным другого пользователя. |
| X-Original-URL | Заголовок для подмены пути. |
| X-HTTP-Method-Override | Заголовок для подмены метода. |
| Безопасность через сокрытие | Плохая практика — надеяться, что URL никто не найдёт. |
| Referer Spoofing | Подделка заголовка Referer. |
| GUID | Глобально уникальный идентификатор — сложно угадать, но можно украсть. |
| Enumeration | Перебор ID для поиска нужного пользователя. |
| RBAC | Контроль доступа на основе ролей. |

---

## 💡 8. Главное правило пентеста

> Всегда проверяй, проверяет ли приложение права на каждом шагу, а не только на входе в систему.

Если функция есть — она должна быть защищена, даже если ссылка на неё скрыта.
