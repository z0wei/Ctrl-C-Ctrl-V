## 📌 1. Что такое аутентификация

**Аутентификация** — это процесс проверки того, что пользователь или клиент действительно является тем, за кого себя выдаёт.

Веб-сайты потенциально доступны любому, кто подключён к интернету, поэтому надёжные механизмы аутентификации являются неотъемлемой частью эффективной веб-безопасности.

---

## ⚖️ 2. Аутентификация vs Авторизация

| Термин | Что делает | Пример |
| :--- | :--- | :--- |
| **Аутентификация** | Проверяет, что пользователь — это тот, за кого себя выдаёт | Проверка, что `Carlos123` действительно создатель аккаунта |
| **Авторизация** | Проверяет, разрешено ли пользователю выполнять действие | Проверка, может ли `Carlos123` удалять аккаунты других пользователей |

> **Запомни:** Аутентификация — это «кто ты?», авторизация — «что тебе можно?».

---

## 🔑 3. Основные типы аутентификации

| Тип | Описание | Примеры |
| :--- | :--- | :--- |
| **Something you know** (Знание) | То, что пользователь знает | Пароль, ответ на секретный вопрос, PIN-код |
| **Something you have** (Владение) | Физический объект в руках пользователя | Мобильный телефон, аппаратный токен, смарт-карта |
| **Something you are/do** (Существование/поведение) | Биометрические данные или паттерны поведения | Отпечаток пальца, Face ID, голос, ритм набора текста |

## 🔓 4. Уязвимости в аутентификации

Большинство уязвимостей аутентификации возникают одним из двух способов:

1. **Слабые механизмы** — не обеспечивают достаточной защиты от атак перебором.
2. **Логические ошибки** — позволяют полностью обойти аутентификацию («broken authentication»).

### 4.1 Уязвимости входа по паролю (Password-based Login)

Сайты, использующие только пароль для аутентификации, могут быть крайне уязвимы, если не внедряют достаточную защиту от атак перебора.

#### 🔹 Брутфорс-атаки (Brute-force attacks)

Атакующий использует систему проб и ошибок для подбора учётных данных, автоматизируя процесс с помощью списков логинов и паролей.

**Перебор логинов (Username enumeration)** — атакующий определяет, существует ли пользователь, по изменениям в поведении сайта:

| Индикатор | Что проверять |
| :--- | :--- |
| **Status codes** | Разный HTTP-статус при правильном логине |
| **Error messages** | Разные сообщения при неверном логине и неверном пароле |
| **Response times** | Увеличение времени ответа при существующем логине |

**Перебор паролей** — учитывает поведение пользователей: они часто используют предсказуемые паттерны (`Mypassword1!`, `Myp4$$w0rd`) и делают минимальные изменения при смене пароля.

#### 🔹 Несовершенная защита от перебора

**Блокировка аккаунта (Account Locking)** — после N неудачных попыток аккаунт блокируется.

**Проблема:** не защищает от атак, где атакующий пытается получить доступ к любому случайному аккаунту. Можно использовать **один и тот же пароль для всех логинов**, чтобы не заблокировать ни один аккаунт.

**Блокировка по IP** — после слишком многих попыток IP блокируется.

**Проблема:** счётчик может сбрасываться при успешном входе → атакующий входит в свой аккаунт каждые несколько попыток.

---

### 4.2 Уязвимости в других механизмах (Other Mechanisms)

Даже если основная страница входа защищена, дополнительные функции могут быть уязвимы.

#### 🔹 «Запомнить меня» (Remember me / Stay logged in)

Генерируется токен, который хранится в постоянной куке. 

**Проблемы:**
- Кука генерируется на основе предсказуемых значений (логин + timestamp)
- Иногда пароль используется как часть куки
- Base64 — это **не шифрование**, а просто кодировка
- Если нет соли, хеш можно взломать перебором
- Украденная через XSS кука позволяет восстановить алгоритм

#### 🔹 Сброс пароля (Password Reset)

**Отправка пароля по email** — крайне небезопасно, так как email не является защищённым каналом.

**Сброс через URL** — менее безопасные реализации используют угадываемые параметры:
```
http://vulnerable-website.com/reset-password?user=victim-user
```
Более безопасно — использовать высокоэнтропийный токен:
```
http://vulnerable-website.com/reset-password?token=a0ba0d1cb3b63d1...
```

**Проблемы:**
- Токен не проверяется повторно при отправке формы
- Токен можно украсть через динамическую генерацию URL (password reset poisoning)

#### 🔹 Смена пароля (Password Change)

Обычно требует ввода текущего пароля и нового пароля дважды.

**Проблемы:**
- Доступ к форме без авторизации
- Имя пользователя в скрытом поле — можно подменить
- Используется для перебора паролей (как в лаборатории)

### 4.3 Уязвимости в многофакторной аутентификации (MFA)

2FA безопаснее однофакторной, но плохая реализация может быть обойдена.

#### 🔹 Псевдо-2FA (Email-based 2FA)

Проверка одного и того же фактора (знания) двумя разными способами — **не является настоящей 2FA**.

#### 🔹 SMS-2FA

Код передаётся по SMS, что создаёт риск перехвата и SIM-swapping.

#### 🔹 Обход 2FA

Если после ввода пароля пользователь уже «вошёл» в систему до ввода кода, можно попробовать перейти на защищённые страницы, пропуская второй шаг.

#### 🔹 Логическая ошибка в 2FA

Кука `account=carlos` после первого шага может быть подменена на другого пользователя при отправке кода:
```http
POST /login-steps/second HTTP/1.1
Cookie: account=victim-user
verification-code=123456
```

#### 🔹 Брутфорс 2FA-кода

Код часто состоит из 4-6 цифр. Без защиты перебор тривиален. Можно использовать макросы Burp или Turbo Intruder для автоматизации.

## 🛡️ 5. Как защитить механизмы аутентификации

### 🔹 Защита учётных данных
- Никогда не передавать логин/пароль по незащищённым каналам
- Принудительно перенаправлять HTTP на HTTPS
- Не раскрывать логины/email в публичных профилях и HTTP-ответах

### 🔹 Надёжные пароли
- Использовать валидатор паролей (например, `zxcvbn` от Dropbox)
- Не полагаться на пользователей — они будут использовать предсказуемые пароли

### 🔹 Предотвращение перебора логинов
- Использовать одинаковые сообщения об ошибках
- Возвращать одинаковый HTTP-статус
- Сделать время ответа неотличимым

### 🔹 Защита от брутфорса
- Ограничение скорости запросов по IP (rate limiting)
- CAPTCHA после нескольких неудачных попыток
- Защита от подмены IP (X-Forwarded-For)

### 🔹 Проверка логики
- Тщательно проверять логику на каждом этапе
- Проверять, что нельзя обойти проверку

### 🔹 Дополнительные функции
- Сброс и смена пароля должны быть так же защищены, как основной вход

### 🔹 Правильная 2FA
- Использовать приложения-генераторы (Google Authenticator) вместо SMS
- Проверять логику 2FA

## 🧠 6. Ключевые термины

| Термин | Объяснение |
| :--- | :--- |
| **Authentication** | Проверка, что пользователь — это тот, за кого себя выдаёт |
| **Authorization** | Проверка, разрешено ли пользователю выполнять действие |
| **Brute-force attack** | Перебор логинов/паролей через систему проб и ошибок |
| **Username enumeration** | Определение существующих логинов по поведению сайта |
| **Account locking** | Блокировка аккаунта после N неудачных попыток |
| **Rate limiting** | Ограничение количества запросов по IP |
| **2FA (Two-Factor Authentication)** | Двухфакторная аутентификация (пароль + код) |
| **MFA (Multi-Factor Authentication)** | Многофакторная аутентификация |
| **Remember me cookie** | Кука для долгосрочной авторизации |
| **Password reset poisoning** | Кража токена сброса пароля через динамический URL |
| **SIM swapping** | Атака на SMS-2FA через подмену SIM-карты |

## 💡 8. Главное правило пентеста

> **Аутентификация — это не только форма входа. Это вся система управления доступом.**

Нельзя просто защитить страницу логина и забыть про всё остальное. Восстановление пароля, смена пароля, «запомнить меня», регистрация — всё это части одной системы, и каждая из них может быть уязвима.

**Всегда проверяй:**
- Можно ли перебирать логины и пароли.
- Можно ли обойти 2FA.
- Можно ли подменить куку «запомнить меня».
- Можно ли сбросить пароль другого пользователя.
- Можно ли изменить пароль без авторизации.
- Есть ли защита от брутфорса и как она работает.
